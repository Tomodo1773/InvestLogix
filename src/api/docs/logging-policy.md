# Logging Policy (API / Loguru)

## 目的

- API実行時に「裏でどんな処理が走っているか」「今どの処理段階か」を把握する
- 失敗時の原因追跡を容易にする
- ログの出し過ぎを避け、必要十分な情報量に抑える

## 対象範囲

- `src/api` のサーバーサイド処理
- FastAPIのデフォルトアクセスログ（リクエスト/ステータス）は対象外とし、自前では追加しない

## ログレベル

- **INFO / ERROR のみ**を使用する
- DEBUG, WARNING などは当面使わない

## 出力方針（どこで出すか）

### 1. 主要ユースケース（ビジネス処理の節）

- 例: ポートフォリオ集計、配当集計、通知送信などの主要処理
- 目的: 処理の流れを追えるようにする
- **INFO** で要所を1〜2行に抑える（開始・終了の全記録はしない）
- 例: 取引登録/配当登録/保有損益更新などで「1回の処理につき1行」のサマリを出す
- テーブル名と action を含め、DBの変化が分かる文面にする

### 2. 外部I/O

- DBアクセス、外部API呼び出し、通知送信など
- 目的: I/Oがどこで行われたか、結果がどうだったかを把握する
- **INFO** で呼び出しの結果（成功/失敗・件数・応答コードなど）を残す
- 例: 株価取得、為替取得、外部API呼び出し結果（symbol, price, count など最小限）

### 2.1 DB中心のログ設計

- テーブル名を文面に含める（例: `Holdingsを取得しました`）
- action を短く固定化する（`select / create / update / bulk_update / aggregate`）
- 件数が取れる場合は `count` を付与する
- select の結果は `found=true/false` で明示する
- 例: `Stockを取得しました action=select user_id=1 symbol=7203 found=true`
- 例: `Dividendに登録しました action=create user_id=1 symbol=7203 dividend_id=10`
- 例: `Transactionを取得しました action=aggregate user_id=1 symbol=7203 total_buy_quantity=100`

### 3. 例外処理

- 例外発生時は **ERROR** を必ず出す
- 例外に関係する文脈（対象ユーザー、対象銘柄、処理名など）を含める

### 4. 集計・一覧取得

- 月次/年次などの集計系は **INFO** で件数のみを出す（ループ内での逐次ログは禁止）
- 例: `months=12` のようなサマリのみ
- 全件更新や一括処理は、ループ内の詳細ログを抑制し、最後にサマリのみ出す

### 5. ビジネス判断による未実行

- 例外ではないが処理を中断する場合は **INFO** を出す
- 例: 売却数量不足、保有データなしなど（reason を短く付ける）

### 6. ログに含める最低限の文脈

- `user_id`、`symbol`、`transaction_id`、`dividend_id` などの主要キー
- 金額系は最小限（必要なときのみ）に限定

## 出さないログ

- すべての関数の開始/終了ログ
- ループ内での逐次ログ
- 認証情報、トークン、個人情報などの秘匿情報

## Loguruの設定

- Loguruの**デフォルト設定**を使用する
- 追加のフォーマットやハンドラ設定は当面行わない

## 運用メモ

- ログは「流れの把握」と「失敗時の原因追跡」が目的
- 詳細な内部状態の記録や逐次ログが必要になった場合は、用途を明確にしてから追加する
